# WPT export

One [testharness.js](https://web-platform-tests.org/writing-tests/testharness-api.html) test per repro in [`../repros/`](../repros), generated by [`tools/export-wpt.cjs`](../tools/export-wpt.cjs) with the model's outcomes as the expected values. They are written to go in WPT's `webmcp/imperative/` as they are. They use the same setup as the tests there: `/resources/testharness.js` and `/resources/testharnessreport.js`, a `.https.html` name, `document.modelContext` used directly with no feature detection, and `promise_test` with `promise_rejects_dom` / `promise_rejects_js`.

**They are ready to submit but have not been submitted.** Three of them take a side on an open spec question (below), which needs settling first.

```
node tools/export-wpt.cjs repros/*.json --focus                                   # regenerate (needs lake build)
node tools/run-wpt-export.cjs <wpt checkout> <target> [dir] [--json <out.json>]   # run them in Playwright
```

`--focus` checks every `Tool` member only in a test's last call, so a test about one finding doesn't fail on an unrelated one first. `run-wpt-export.cjs` serves the tests over `http://localhost` next to the WPT checkout's `resources/testharness.js` and `testharnessreport.js` and reads the results from a completion callback, as wptrunner does. For a polyfill target it injects the polyfill before the page's scripts, as the polyfill's own WPT runner does with `--inject-script`.

## The #361 tests

`361-string-result`, `361-empty-string-result` and `361-undefined-result` encode the spec as written: `executeTool()` resolves with the JSON serialization of the callback's result, and rejects with `OperationError` when it has none. That's the open question in [webmcp#361](https://github.com/webmachinelearning/webmcp/issues/361). Chromium stringifies primitives instead, and three existing WPT tests (at e00a7b1) assert Chromium's behaviour:

- `webmcp/imperative/object-arguments.https.html` expects `"Success"` from a tool returning `"Success"`
- `webmcp/imperative/executeTool-abort.https.html` expects `'success'` from a tool returning `'success'`
- `webmcp/imperative/exposedTo-invalid-origins.https.html` expects `'callback2'` from a tool returning `'callback2'`

Run the same way, those three pass in Chromium 157 and fail in the polyfill PR #25, which gets `"\"Success\""` and so on (`../results/wpt-existing-361-*.json`). So the exported #361 tests would fail in Chromium and contradict those three. Submit them only once #361 settles on the spec's current text; if it settles on Chromium's behaviour, the spec and the model change instead, and these three tests get regenerated with the new expectations.

The other seven don't depend on #361.
